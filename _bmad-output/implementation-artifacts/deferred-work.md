- **🐛 `[target.'cfg(debug_assertions)'.dependencies]` does NOT strip `bevy_egui` from release builds** — Cargo emits this warning on `cargo check`:
  `warning: Found 'debug_assertions' in target.'cfg(...)'.dependencies. This value is not supported for selecting dependencies and will not work as expected.`
  Cargo evaluates `cfg()` predicates in dependency tables BEFORE rustc-flag processing, so `debug_assertions` is treated as always-true and `bevy_egui` is pulled into every build (debug AND release). The Blind Hunter and Edge Case Hunter both raised this in the original 2026-04-22 review; both findings were incorrectly dismissed under the assumption that the cargo compile success implied correct semantics. The compile DID succeed — but the design intent ("dev-only egui, stripped from release") is silently broken.
  **Source of error:** the `Cargo.toml Skeleton` in story 1.1's Dev Notes (and presumably the upstream `architecture.md`) prescribes this exact (broken) pattern. Architecture doc may need an erratum.
  **Candidate fixes (architectural, NOT a Story 1.1 micro-patch):**
  1. Move `bevy_egui` to `[features] dev-tools = ["dep:bevy_egui"]` and run dev with `cargo run --features dev-tools`. Clean, explicit, but requires a features-section convention.
  2. Move `bevy_egui` to `[dev-dependencies]`. Only available in tests/examples — does NOT solve the "I want it in `cargo run` debug" use case.
  3. Keep `bevy_egui` as an unconditional dep, gate USAGE in Rust code with `#[cfg(debug_assertions)]`. Egui still in Cargo.lock and compile graph for release (binary bloat persists), but at least no runtime overhead.
  Recommended: option 1 (feature flag) — but defer to Story 1.5 (first time the egui plugin actually gets registered) so the fix and the first usage land together.

## Design question raised during 3-10 dev-story (2026-05-05) — asteroid fragmentation

- **Asteroids vanish on hit instead of fragmenting (classic Asteroids-style breakdown)** — `src/combat/damage.rs::apply_asteroid_damage`. Story 3.10 implements the Epic 3 spec literally: `AsteroidHp.current == 0` → `commands.entity.despawn()` + emit `AsteroidDestroyed { asteroid: Entity }`. No visual debris, no smaller-asteroid spawn. Till noted that classic Asteroids has a large→medium→small fragmentation chain; the project name `asteroids3D` implies the heritage. **Plan-level finding:** PRD line 204 narrative ("He fires. It fragments.") mentions fragmentation poetically, but no FR captures it; FR12 covers projectile-damage-to-debris but FR7's "debris" is a separate entity class spawned by who-knows-when. The current planned answer to "what happens on destroy" is FR13 / Story 6.11's intact-vs-destroyed yield asymmetry (intact tractor-capture awards more salvage than shooting), NOT fragmentation. **Resolution paths (pick one if/when revisited):**
  1. **Polish-only VFX (cheapest, recommended)** — add a particle-burst on `AsteroidDestroyed` event in Epic 10 polish (sibling to Story 10.6 shield-absorb VFX). No new entity class, no yield-math changes, no Avian load increase. Buys ~80% of the visceral feedback for ~5% of the engineering cost.
  2. **Spawn `Debris` entities (medium, design-impact)** — on AsteroidDestroyed, spawn 2–4 child Debris entities with `Debris` Component (FR7 already names this class), inheriting parent velocity + random spin + smaller scale. Debris is shoot-able / tractor-able / TTL'd. **Costs:** new component, new spawn system, Avian narrow-phase load (17 → potentially 50+ entities), interaction with Story 6.10 tractor-beam (debris-tractoring vs intact-tractoring), interaction with Story 6.11 yield math (does debris give sub-yield? cumulative yield identical to intact-capture defeats FR13's incentive). Best slotted post-MVP between Epic 7 and Epic 8.
  3. **Full fragmentation chain (heavy, Asteroids-faithful)** — large → 2× medium → each medium → 2× small. Each fragment has its own AsteroidHp + visual mesh + AsteroidCaptured eligibility. **Costs:** SizeCategory component (Story 6.11 already plans this), spawn-on-destroy system, Avian load explosion (17 large → 17×4 = 68 entities at full breakdown), full re-evaluation of Story 6.11 yield math (sum-of-fragments vs single-intact-capture must preserve FR13's "intact > destroyed" invariant), tractor-beam UX (which fragment to grab?). Belongs in a dedicated post-MVP epic if pursued.
  
  **Till's preference (2026-05-05):** undecided; option 1 flagged as default if/when polish-pass timing arrives. Re-evaluate at Epic 10 entry (M9). Source: design question raised by Till during 3-10 dev-story handoff.
